# 项目权限管理

## 目标

项目权限用于控制普通成员在单个项目内可以执行的 Skill 操作。团队 Owner 和 Admin
始终拥有完整项目权限，并负责维护普通成员策略。

项目权限与团队 Skill 仓库权限相互独立：

- 项目策略只作用于当前项目中的关联、部署和协作操作。
- 团队 Skill 仓库是团队共享资产，不属于某一个项目。
- 团队 Skill 可被所有团队成员读取，但直接编辑、删除、资源写入和版本恢复仅允许
  Owner/Admin。

## 角色规则

### Owner / Admin

- 始终拥有所有项目操作权限。
- 可以读取和更新项目权限策略。
- 可以编辑、删除项目。
- 可以直接修改或删除团队 Skill。

项目策略中的关闭项不会限制 Owner/Admin，避免管理员将自己锁出管理流程。

### Member

- 可以查看项目信息、关联 Skill 列表、部署状态和项目动态。
- 项目写操作由当前项目的普通成员策略决定。
- 团队 Skill 仓库保持只读。

### 非团队成员

不能读取项目、权限策略或团队 Skill。

## 项目操作权限

权限键是稳定的 API 契约：

- `add_skill`：将团队 Skill 关联到项目。
- `remove_skill`：从项目移除已关联 Skill。
- `deploy_skill`：部署、重新部署、构建制品及登记部署。
- `push_changes`：将本地改动推送到团队仓库；自动提升操作按此权限处理。
- `pull_updates`：拉取团队版本并更新本地。
- `merge_conflicts`：分析、应用和提交冲突合并。
- `manage_tracking`：停止或恢复本地跟踪。

只读查询、同步状态、变化记录和 WebSocket 通知不受这些开关限制。

## 默认与兼容

权限策略使用独立的 `ProjectPermissionPolicy` 记录。项目不存在策略记录时，七项普通成员
权限全部视为开放，以保持历史项目升级前后的行为一致。

管理员首次保存时才创建策略记录。服务端会忽略存储中未知的旧字段，并拒绝 API 请求中
未知的新字段，防止拼写错误导致策略静默失效。

## API

### 读取策略

`GET /api/v1/projects/{project_id}/permissions`

团队成员均可调用。响应包含：

- `member_permissions`：管理员为普通成员配置的原始策略。
- `effective_permissions`：当前调用者最终生效的策略。
- `role`：当前调用者的团队角色。
- `can_manage`：是否可以修改策略。
- `updated_by`、`updated_at`：最近更新信息。

Owner/Admin 的 `effective_permissions` 始终全部为 `true`。

### 更新策略

`PUT /api/v1/projects/{project_id}/permissions`

仅 Owner/Admin 可调用。请求必须完整提交七个布尔值；保存采用整体替换，避免 JSON
字段原地修改未被 ORM 跟踪。

## 强制执行

前端禁用按钮仅用于解释当前状态，不能替代授权。所有写端点必须在后端执行统一检查：

1. 根据项目或 deployment 查出项目。
2. 重新确认调用者仍是项目所属团队成员。
3. Owner/Admin 直接放行。
4. Member 根据项目策略判断操作键。
5. 拒绝时返回 HTTP 403，并指出被关闭的操作。

deployment 的用户归属检查继续保留；项目权限检查是额外的团队授权边界。

## 前端行为

“项目管理”页按 Skill 管理、本地部署、协作同步展示权限开关。管理员可以整体开放或关闭，
修改后通过保存条统一提交；普通成员看到只读策略。

项目内受限操作按钮保持可见但不可点击，并提示“管理员已关闭此权限”。这样成员可以理解
功能存在但当前无权使用。项目编辑和删除入口只对 Owner/Admin 显示。

团队 Skill 详情页对普通成员显示只读状态，编辑、删除、资源修改和版本恢复入口不展示；
后端仍会拒绝绕过界面的直接请求。
