## 2. 七端点实现与契约对应

> 所有 HTTP 响应实际为 `LocalAgentResponse<T>`（成功 `T` | 统一失败 `LocalAgentFailure`）。成功响应含 `ok:true` + `apiVersion`；失败含 `ok:false` + `error{code,message,detail?}`。

| # | 方法 + 路径 | 鉴权 | 实现 | 契约对应 | 关键点 |
| --- | --- | --- | --- | --- | --- |
| 1 | `GET /local/health` | **无** | `handlers/health.ts` | §2 `HealthResponse` | 唯一免令牌；返回 agentVersion/apiVersion/platform/paired/平台 skill 目录（解析用户 home） |
| 2 | `GET /local/browse?path=` | 配对令牌 | `handlers/browse.ts` | §3 `BrowseResponse` | 精确复刻后端 `browse_directory`：空 path→Windows 盘符/POSIX `/`；过滤非目录/`.`开头/`node_modules,__pycache__,.git,dist,build`；无权限→`dirs:[]`+`note:"权限不足"`；**副作用：登记 current 与子目录为可写根** |
| 3 | `POST /local/scan` | 配对令牌 | `handlers/scan.ts` + `scan/*` | §4 `ScanResponse`/`UnifiedSkillPackage` | 纯 TS 扫描 + 来源识别（R1）；输出 camelCase 直接对齐契约 |
| 4 | `POST /local/read-folder` | 配对令牌 | `handlers/readFolder.ts` | §5 `ReadFolderResponse` | 递归读取；`root=realpath`；`dirHash` 对全量算；`include=skill\|all`（默认 all）；文本 utf8 / 二进制 base64 |
| 5 | `POST /local/write-skill` | 配对令牌 **+ 白名单** | `handlers/writeSkill.ts` | §6 `WriteSkillResponse` | 覆盖语义（先 rm -rf 再写）；contents 文本 + resources（inline base64/utf8）；`ensureGitignore`（仅 project）；落盘后即算 `installedHash` |
| 6 | `POST /local/hash` | 配对令牌 | `handlers/hash.ts` | §7 `HashResponse` | 逐路径统一算法；不存在/空目录→`hash:""`，`exists` 反映真实存在性 |
| 7 | `WS /local/watch` | 配对令牌 | `handlers/watch.ts` | §8 `WatchClientMessage`/`WatchServerMessage` | 握手校验 `X-Pairing-Token` 或 query `pairingToken`；subscribe/unsubscribe/ping；防抖 1s + 安全轮询 3s；`dirty = exists && currentHash != installedHash` |

### 2.1 install 路径推导（对齐 `project_service._install_root` :72-78）

- `scope=project`：`{deployPath}/.{tool}/skills/{skillId}`
- `scope=platform`：`{平台 skill 目录}/{skillId}`（忽略 deployPath）
  - cursor → `~/.cursor/skills`；codex → `$CODEX_HOME/skills`（未设则 `~/.codex/skills`）——与 `native_skill_store.py:31-34` 一致。

### 2.2 资源传输（D1）

- M3 仅实现 **`transfer:"inline"`**（`encoding`+`content`，base64/utf8），与协调者 D1 决议「先 A 内联」一致。
- 契约预留的 **`transfer:"url"`** 在 M3 显式返回 `BAD_REQUEST`（"transfer=url 暂未实现"），字段保留以便 M5 无痛切换（带 Bearer 向云端下载后校验 sha256 落盘）。
- **【已决议】** M3 维持 inline；切 `url`（对象存储 + 带 Bearer 下载）**推迟到后期（M5 之后）**。详见 `M2-评审决议与上线清单.md` §7 决议⑥ / §8 M5 待办。

| code | HTTP | 触发点示例 |

## 3. 安全 / 配对模型（M0 §5）

### 3.1 仅监听 127.0.0.1（§5.4）

- HTTP/WS socket **只绑定 `127.0.0.1`**（`server.ts` 常量 `HOST`），杜绝局域网访问。
- **CORS**：仅放行 `file://` / `app://` / `http(s)://127.0.0.1|localhost` / `vscode-webview://` 来源；其他网页跨站调用不返回 CORS 头（浏览器拦截）。`OPTIONS` 预检返回 204。

### 3.2 配对令牌（双令牌分离，§5.2 / D2）

- 本地代理**只认配对令牌**（请求头 `X-Pairing-Token`），**不认云端 Bearer**。
- 校验：`auth.ts::verifyPairingToken(provided, expected)` —— 双方非空且 `constantTimeCompare` 相等，**语义对齐后端 `core/security.py`**（`hmac.compare_digest`：UTF-8 字节、空值拒绝、长度不同判负）。TS 侧用 `crypto.timingSafeEqual`（长度不同时做一次等长自比较再判负，避免泄露差异位置）。
- 注入（CLI > env > dev 默认）：
  - `--pairing-token=<token>` 或 `VIBEBARA_PAIRING_TOKEN`（M5 由 Electron 主进程注入高熵 `pairingSecret`）。
  - **未注入** → 使用固定**开发默认令牌**（`vibebara-dev-insecure-pairing-token-change-me`，仿 M2 JWT dev 默认风格：固定常量、重启不失效），启动打印**告警**，且 `health.paired=false`。
- `auth.ts::generatePairingToken(32)` 提供高熵令牌生成器（对齐 `generate_pairing_token`），供联调脚本/主进程复用。

### 3.3 可写根白名单（§5.3）

- `security.ts::WritableRoots`：写操作目标路径必须经 `realResolve`（解析已存在前缀的 realpath，防符号链接逃逸）后落在某已登记根之内。
- 白名单来源（三者并集）：
  1. **启动注入**：`--writable-root=PATH`（可重复）/ `VIBEBARA_WRITABLE_ROOTS`（`;`/`,` 分隔）。
  2. **平台 skill 目录**：`~/.cursor/skills`、`~/.codex/skills` 在 `createContext` 时自动登记（`scope=platform` 始终可写）。
  3. **运行期登记**：每次 `GET /local/browse` 把 `current` 目录与其列出的子目录登记为候选可写根——这正是契约 §5.3 允许的「本地代理在 write-skill 时按"用户最近确认过的目录"校验」，**因而无需新增契约外端点**（7 端点冻结不变）。
- **逃逸防护**：
  - `installPath` 经 `realResolve` 后用 `isInside` 判定包含（Windows 大小写不敏感）；不在白名单 → `WRITE_ROOT_FORBIDDEN`。
  - 每个 contents/resources 条目路径经 `safeJoinUnder` 校验：禁止绝对路径、盘符路径、`..`，拼接后必须仍在 installPath 之内；违规 → `BAD_REQUEST`。
  - `skillId` 禁止含 `/ \ ..`。

## 4. hash 一致性验证（命门，§7）

### 4.1 算法复刻（`hash.ts` + `walk.ts`）

逐条对齐云端冻结实现（`_compute_content_hash` / `_compute_dir_hash`，已含 R2 收敛）：

1. root 不存在 → `""`；root 是文件或空目录 → `""`（对齐 `Path(file).rglob("*")` 产出空）。
2. 递归收集所有**常规文件**（含隐藏文件；排除目录；symlink→file 计为文件，symlink→dir 不递归——对齐 Python `rglob` 不跟随目录软链 + `is_file()` 跟随）。
3. 相对 root 的 **POSIX** 路径（`path.relative` 后 `split(sep).join('/')`）。
4. **按相对路径 UTF-8 字节序升序排序**：`Buffer.compare(Buffer.from(x,'utf8'), Buffer.from(y,'utf8'))`（**不**用 `localeCompare`/默认 `<`，避免 UTF-16 码元序与 UTF-8 字节序分歧）——这是 §7.2 R2 排序键收敛的关键。
5. 流式 sha256：每文件 `update(utf8(rel))` → `update(0x00)` → `update(原始字节)` → `update(0x00)`。
6. 小写 hex 输出。
7. 文件名 Unicode **不做 NFC/NFD 归一**（与 `as_posix()` 一致；R3 **已决议**：当前 Windows-first，macOS NFD 文件名两端 hash 一致性专项验证推后——详见 `M2-评审决议与上线清单.md` §7 决议⑦ / §9 范围约束）。

`hash` 与 `read-folder` 共用 `walk.ts::walkFiles`，杜绝两处遍历口径漂移。

### 4.2 跨语言位级一致实测

构造与 `backend/tests/test_hash_convergence._build_tree` **字节一致**的目录树（含：分隔符排序陷阱 `ref/z` vs `refA.md`、中文目录/文件名 `资料/说明.md`、兼容 Windows 的大小写排序边界 `Aa.txt`/`aB.txt`、1024 字节二进制 `assets/icon.png`），分别用本地代理 TS 实现与云端 Python 参考算法计算：

```
TS（local-agent computeDirHash）= 37b702e386cff1ded780b07b2c679aabdfadf83a93e2d5fbc8dc931268cf394a
PY（backend §7.3 参考实现）     = 37b702e386cff1ded780b07b2c679aabdfadf83a93e2d5fbc8dc931268cf394a
```

**完全相等**。该 hex 作为 `CLOUD_PARITY_HEX` 常量固化进 `test/hash.test.ts`，每次跑测试即回归「与云端位级一致」。`hash.test.ts` 另含一份独立的 §7.3 内联参考实现做双重交叉验证（不复用生产代码）。

### 4.3 端到端一致性（冒烟实测）

write-skill 落盘后返回的 `installedHash` 与随后 `POST /local/hash` 对同一 installPath 的结果**完全相同**（实测 `eda591c2012b90e31f533b5f8b645807b75c04f12573d6243ad3017d35bce0b2`），证明「落盘即算」与「独立算」一致，dirty 检测基线稳定。

## 5. scan 来源识别移植（R1 / D3）

> D3 决议：scan 纯 TS 下沉本地代理（避免大目录全量上传）。R1：把 Node bridge `scan-and-package` 的 origin 检测 / 包结构识别 / 资源归一化逻辑用纯 TS 复刻（**不内嵌构建管线**）。

移植映射（逐函数对齐，便于云端复用、与现有 `scan-and-package` 输出结构对齐）：

| 本地代理（TS） | 移植自 | 说明 |
| --- | --- | --- |
| `scan/frontmatter.ts::parseFrontmatter` | `skill-forge/src/utils/yaml.ts` | 同正则 `^---\r?\n…\r?\n---\r?\n…$` + `js-yaml.load`，保证 frontmatter 解析口径一致 |
| `scan/detect.ts::detectOrigin` | `skill-forge/src/adapters/detect.ts` | **逐字移植**评分模型：agents/openai.yaml(+3 codex)、disable-model-invocation(+3 cursor)、metadata.short-description(+1)、`$skill-name` 引用(+2)、assets/(+1)、references/+agents/(+1)、flat reference.md/examples.md(+2 cursor)；置信度 high/medium/low 判定一致 |
| `scan/scan.ts::packageSkill` | `skill-forge/src/commands/package.ts::packageSkill` | id=basename；`importFrom = origin==="unknown"?"codex":origin`；资源用 `readdir` 列直接条目；installedAt 探测 `~/.cursor|.codex/skills/{id}/SKILL.md` |
| `scan/scan.ts::extractConfigFields` | `skill-forge/src/commands/import.ts::importFrom{Cursor,Codex}` | 仅提取契约所需字段（name/description/displayName/shortDescription）：cursor 不含 displayName/shortDescription；codex 取 metadata.short-description + agents/openai.yaml interface.{display_name,short_description}（>256 截断） |
| `scan/scan.ts::scanAndPackage` 的归一化输出 | `backend/skill_forge_service.py::SkillRegistry._normalize_packages` | 直接产出契约 camelCase `UnifiedSkillPackage`：`name=config.name\|\|id`、`displayName/description/shortDescription` 缺省 `""`、`hasScripts/References/Assets = readdir(...).length>0`、`installedAt{cursor,codex}` |

`scanAndPackage(rootDir)`：列一级子目录（跳过 `.` 开头）→ 仅保留含 `SKILL.md` 者 → 逐个 `packageSkill`；单个解析失败不影响整体（对齐 bridge 行为）。

**风险评估**：移植为「重写不依赖构建管线的扫描模块」，未引入 skill-forge 依赖，体积小。**残留风险**：
- 评分模型若云端 bridge 后续演进，需同步本地代理 `detect.ts`（建议两端共享同一测试夹具）。
- `installedAt` 探测的是**用户机器**平台目录（与后端旧实现探测后端盘语义不同，但正是迁移目标——云端不再探测自身磁盘，改由本地 scan 上报，对应 M0 §2.3 `_upsert_db` 改造）。

## 6. 与云端编排的对接点（M4 前端编排所需）

> 前端是唯一编排者：对云端持 Bearer、对本地代理持配对令牌。下表给出 M3 端点在六条数据流中与**云端 DTO（契约 §9，云端实现属 M1）**的配合关系。

| 数据流 | 本地代理端点 | 配合的云端 DTO（§9） | 字段流转要点 |
| --- | --- | --- | --- |
| **deploy**（§3.1） | `write-skill` → `hash`（或 write-skill 顺带返回 `installedHash`） | `BuildArtifactResponse`（云端产 contents+resources+repoHash+repoVersion+abstractSnapshot）→ `RegisterDeploymentRequest`（回报 installPath+installedHash+repoHash+repoVersion+abstractSnapshot） | `installedHash` 本地算（权威）；`abstractSnapshot` 由云端从产物直接生成（D4-A，免本地回传） |
| **pull-update**（§3.3） | `hash`（前置冲突检测）→ `write-skill`(overwrite) → `hash` | `BuildArtifactResponse`（团队最新）→ `CommitPullRequest`（installedHash+repoVersion+repoHash=teamHash+abstractSnapshot） | 覆盖写后本地重算 installedHash 回报 |
| **push**（§3.2） | `hash`（判定是否真改动）→ `read-folder`(install 全量) | `PushDeploymentRequest`（currentHash + files[] 含 base64） | 本地内容云端不可知，必须 read-folder 上传；abstractSnapshot 必须云端解析回传内容（D4-B） |
| **promote**（§3.2 同 push） | `read-folder` | 复用 push 链路 | 同 push |
| **scan**（§3.4） | `scan` | 无（纯本地）；结果供云端 `_upsert_db` 接收 `installedAt` | 云端不再探测自身磁盘 |
| **import**（§3.5） | `read-folder` | `ImportContentRequest`（files[] + origin? + scope + teamId?） | 读取上传，解析/入库权威在云端 |
| **dirty/watch**（§3.6） | `WS /local/watch`（实时）/ `hash`（按需） | 现有 `local-status` 语义（云端比对前端上报的 currentHash/exists） | dirty 一律本地两次 hash 比较；云端不轮询本地盘 |

> `FilePayload`（read-folder 输出）与 `ResourcePayload`/`contents`（write-skill 入参）的编码约定（§4.5）与云端 `CloudResourceItem` 对齐：文本 utf8 原样、二进制 base64、逐字节忠实落盘。

- **§7.4 云端预测 installed_hash 优化**：M3 **默认不启用**（R4：以本地实算为权威，最稳妥）。两端 hash 已验证位级一致，后续如需省一次 `/local/hash` 往返，可由云端在 build 阶段预测，本地代理无需改动即可兼容。

## 10. 遗留给 M4（前端编排分流）的对接说明

1. **拆两个 client**：云端 client（Bearer、云端域名）+ 本地代理 client（`http://127.0.0.1:<PORT>`、`X-Pairing-Token`）。端口由 M5 主进程注入；M4 可先通过 `GET /local/health` 探测/确认端口与 `apiVersion`。
2. **deploy/pull/push 重写为多步编排**（按 §6 表）：原 `projects.ts` 的 `deployProjectSkill/pushDeployment/pullUpdateDeployment` 等单次云端调用，改为「云端产物 → 本地 write-skill → 本地 hash → 云端登记」链路。
3. **白名单触发约定**：前端在用户选定部署目录时，应先调 `GET /local/browse` 浏览到该目录（或其父目录），使本地代理登记可写根，随后 `write-skill` 才会放行；否则返回 `WRITE_ROOT_FORBIDDEN`。（若 M4 希望更显式的「确认部署目录」交互，可在 M5 评估是否新增登记端点——M3 选择复用 browse 以保持 7 端点冻结。）
4. **watch 订阅**：本地 dirty 监控走 `WS /local/watch`（subscribe `{deploymentId, installPath, installedHash}`），收到 `changed/missing` 后按现有 `local-status` 语义更新云端 `local_dirty`；云端项目实时广播仍走云端 WSS。
5. **错误处理**：前端统一按 `LocalAgentFailure.error.code` 分支提示（401 引导重新配对、403 引导重新选目录、409 提示已存在等）。
6. **版本协商（§6.3）**：M4 启动自检 `GET /local/health.apiVersion` + 云端 `GET /api/v1/version.minClientVersion`，不兼容时禁用写流程（deploy/push/pull/write-skill），只读浏览仍可用。

### 评审决议与周知事项（已决议）

> 三项「需协调者拍板」已于 M3 收尾评审中**最终决议**，结论如下逐条标注【已决议】并写明归属（M5 / 后期）。决议全文与后续待办登记见 `docs/archive/desktop-migration/M2-评审决议与上线清单.md`：§7「M3 评审决议」（决议⑤⑥⑦）、§8「M5 待办登记」、§9「范围约束」。R2 / R4 为周知事项（非待拍板）。

- **白名单登记机制【已决议】**：**采纳 M3 现状「browse 即登记」**——用户经 `GET /local/browse` 浏览/选定目录即登记为可写根，以保持本地代理 **7 端点冻结不变**（不新增契约外端点）。"显式注册端点"的评审**并入 M5（桌面交互阶段）** 再定。
- **D1 资源传输【已决议】**：M3 **维持 inline（base64 内联）**；大体积二进制资源切 `transfer:"url"`（需云端对象存储 + 本地带 Bearer 下载并校验 sha256 落盘）**推迟到后期（M5 之后）**，`url` 字段已在契约预留（M3 对 `transfer=url` 显式返回 `BAD_REQUEST`），可无痛切换。
- **R3 文件名 Unicode / 跨平台【已决议】**：当前 **Windows-first**；文件名 Unicode 统一不做 NFC/NFD 归一（口径不变），**macOS NFD 文件名两端 hash 一致性专项验证推后**，待将来覆盖 macOS 时再做。
- **R2（云端必做 · 周知）**：M3 hash 与「云端已收敛实现」位级一致已验证；云端 M1 两处 `sorted(...)` 的 UTF-8 字节序收敛（`project_service`/`native_skill_store`）须保持，勿回退，否则跨平台/中文名 dirty 误判。
- **R4 installed_hash 权威（周知）**：默认本地实算；§7.4 云端预测优化两端已具备一致性前提，是否启用由后续按性能需求决定。
